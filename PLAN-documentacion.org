#+TITLE: Plan de reorganización de la documentación de qbank
#+AUTHOR: Marcos Bujosa
#+LANGUAGE: es
#+STARTUP: overview

Plan vigente para que un profesor pueda crear su propio banco de preguntas
con =qbank= siguiendo solo la documentación, sin asistencia de una IA.
Redactado el 19 de octubre de 2026 tras revisar =qbank=, =qbank-econometria=
y =qbank-PEconometria=. Cada fase lleva su estado; al cerrar una, marcarla.

* Diagnóstico

No falta documentación (README, Manual, tres notebooks, dos =.org=
literate, y en los bancos privados un tutorial, un prompt genérico y uno
específico: unas 7.000 líneas). El problema es *dónde* está cada cosa y
*qué modelo mental* enseña:

1. La trampa conceptual principal no está en la documentación pública: una
   lista de =Cuestion= sortea *una* por variante; para mostrar cuatro
   opciones hacen falta cuatro elementos-Cuestion consecutivos. Solo lo
   explica =qbank-PEconometria/PROMPT-qbank-generico.org= (privado, escrito
   para una IA). El «Ejemplo mínimo» del Manual y el «Uso rápido» del README
   producen variantes con una sola opción sin comentarlo.
2. El campo =export= (=last_choice=, =cols=, =instances=), la regla de
   =instances= y que =seed= solo actúa con =np.random= no aparecen en el
   Manual ni en el README; los ejemplos del Manual usan =random=.
3. No hay proyecto de arranque: el flujo real (=preguntas/*.json= +
   =scripts/gen_*.py= + =Makefile= + =make lint=) vive duplicado en los dos
   bancos privados y en ningún sitio público.
4. Dos modelos de autoría (listas Python / JSON) sin decir cuál es el camino
   recomendado para un banco.
5. El diseño pedagógico (patrón 3 cuestiones + =last_choice=, garantía de
   mezcla, gemelas V/F, =exp= por mundo, autocontención, trampas
   LaTeX/Moodle) solo está en el prompt genérico, mezclado con fechas y
   referencias a lecciones concretas.
6. Inconsistencias menores: =@a= frente a =@{a}=, rutas de salida erróneas,
   encabezados vacíos, ruta absoluta al =.venv=, bloques literate con API
   antigua (=ProblemaTipoProfe=, =AMCmcProfe=) en =CalcPropExport.org=.

* Decisiones

** D1 — La plantilla de banco vive dentro de qbank, como datos del paquete

Tres opciones valoradas:

- /Carpeta en el repo/ (=plantilla-banco/=): la más simple, pero solo la ve
  quien clona; quien hace =pip install= no la tiene.
- /Repo aparte/ (=qbank-plantilla=, botón «Use this template» de GitHub):
  arranque cómodo, pero se desincroniza del motor (los scripts copiados a
  los bancos ya se rompieron una vez al retirar =opc=), no tiene tests y es
  un repositorio más que mantener.
- /Datos del paquete + orden =qbank-init DIR=/ (*elegida*): la plantilla se
  distribuye con cada versión del motor (la que llega con 0.6 funciona con
  0.6), está disponible tanto con =pip install= como con =git clone=, y los
  tests de qbank ejecutan sus scripts sobre sus preguntas de ejemplo, de
  modo que un cambio de API no puede romperla sin que se note. Coste: la
  carpeta =src/qbank/plantilla/= y una orden de unas 30 líneas que la copia.

** D2 — JSON es el formato de almacenamiento; Python es el formato de autoría

- *JSON* sigue siendo lo que se guarda en =preguntas/= y lo que consumen
  =lint=, los scripts y el =Makefile=: es lo que ya existe (110 preguntas
  en dos bancos), lo que una IA escribe con fiabilidad, y lo que valida el
  lint. No se migra nada.
- *Listas Python* son más legibles para una persona: =v('A')= sin
  comillas, cadenas crudas =r"$\mathcal{A}$"= sin doblar barras (en JSON
  cada =\= es =\\=, la fuente de errores más común al escribir LaTeX a
  mano), comentarios, =setup= como código con resaltado.
- Por tanto: la documentación *enseña con listas Python* y muestra el JSON
  equivalente una vez completo (y después solo donde un campo es propio del
  JSON: =export=, =seed=, =setup= como cadena). El flujo recomendado para
  quien prefiera Python es «escribe la lista en un =.py=, ejecútalo, y
  =save_problema= deja el JSON en =preguntas/=»; la plantilla incluye ese
  =nueva_pregunta.py=. Quien prefiera escribir JSON directamente puede
  hacerlo.
- Requisito técnico: =ProblemaTipo(..., setup="código")= debe aceptar el
  =setup= como cadena (hoy solo lo hace =load_problema=) para que un
  problema escrito en Python con =setup= pueda guardarse en JSON.
- Esta decisión se valida en la fase 5 con un usuario nuevo; cambiarla es
  barato porque =save_problema= y =problema_to_python= convierten en ambos
  sentidos.

** D3 — Material retirado del repositorio

Quitado el 19 de octubre de 2026 (queda en el historial de git):
=examples/= (scripts con API inexistente; los bloques equivalentes siguen
en =CalcPropExport.org= como prosa, ya sin =:tangle=), =legacy/= (módulo
=prop.py= anterior a =calcprop=, preámbulo y ejemplo con API antigua),
=css/= (temas solo usados por =legacy=), =Ejemplos.org= (versión vieja de
=Ejemplos.ipynb=; su única sección extra, el editor visual, está en
=Demo.ipynb=).
